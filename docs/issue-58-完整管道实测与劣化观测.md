## 3. LLM 阶段加速比：1.18×，未达 2× 通过线

冻结输入（09-23）双后端同负载实测（bench_ab.py 沙箱，归档 jsonl 备份/恢复，生产零污染）：

| leg | step4 | step7 | 合计 | 加速比 |
|---|---|---|---|---|
| kvmem (IQ2_S) | 236.5s | 10.5s | **247.0s** | 基准 |
| qwen-local (IQ3_XS 旧栈) | 259.3s | 31.4s | **290.7s** | **1.18×** |

与 #57 的独立实测（kvmem 212.8s vs 旧栈 272.2s = 1.28×）交叉验证：**加速比稳定在 1.2× 上下，两轮实测均未达 2× 通过线**。

分解：
- step4 加速 1.10×（236.5 vs 259.3）——step4 耗时主要是 69 条 ×（涉华判定+评分+分类）串行短调用的**排队延迟**，两后端单次短延迟差距（0.25s vs 0.67s，#57 微基准）被服务端排队/模型加载摊薄；
- step7 加速 3.0×（10.5 vs 31.4）——中等输出场景 KVMem 优势显著，但 step7 占比小，拉不动总加速比。

**判定：未达 ≥2×**。2× 通过线的隐含前提（短调用延迟 2.7× 优势传导到全链）不成立——step4 的 wall time 由 LLM 调用次数 × 单次延迟决定，而单次延迟中 prefill（~0.3-0.6s）与生成（MTP 加速后）对两后端差距有限，差距主要在小输出 token 数与排队策略上。

## 4. 劣化观测：~30 轮红线未复现

数据面（累计 **97 轮**有效请求，覆盖三种负载形态，跨度约 2.5 小时）：

| 轮段 | 载荷 | t/s 范围 | 说明 |
|---|---|---|---|
| seq 1-8 | 修后重启自检/冒烟 | 50.1-84.3 | 256-token 生成与探针模板轮 |
| seq 9-35 | 生产管道 + kvmem leg（step4 全套 26 次 LLM 调用含 n_gen=3053 截断轮 + step7） | 34.5-92.5 | 有效轮 min 34.5（n_gen=10 边界轮），中长输出稳定 87-92 |
| seq 36-67 | 30 轮标准探针（Daily 风格负载 3 模板轮换） | 54.5-90.7 | 无下滑趋势 |
| seq 68-97 | 第二轮探针 + 恢复后自检 | 55.6-97.7 | 无下滑趋势，中位 81.7 |

**判定标准**：有效轮（n_gen≥8，排除单 token MTP 固定开销伪影）连续 3 轮 <30 t/s。

**结果**：97 轮中连续慢轮最长 1 轮，未出现任何 2 连慢轮，更无 3 连；t/s 曲线平稳（每轮探针数据见 `kvmem-degrade-curve.json` / `kvmem-degrade-probe30.json`）。

**结论：Daily 短调用模式不复现 ~30 轮劣化**。红线场景（长上下文 H3，ctx 填充到数十万 token 级）与 Daily 负载形态（n_prompt 23-1483，大部分 <600）差异显著——劣化推测与 KV cache 累积/长上下文管理相关，Daily 的短上下文 + 频繁新会话模式不触发。

## 5. run_all.sh 决定：不加自动重启；修复了更前置的生命周期缺陷

- **不加 step4/step7 间自动重启**（每次 +25s）：前提"证实劣化"不成立（§4），97 轮实测无劣化迹象，重启纯属浪费。保留观测能力：后续任何怀疑劣化的时刻，`python3 bench_kvmem_degrade.py parse --log /tmp/kvmem-daily.log` 即可复检（判定逻辑已固化+单测覆盖）。
- **本次实际修复**（跑管道的前置条件）：run_all.sh 的 LLM 生命周期仍硬编码 `8899`（旧栈），而 `llm.yaml` 已 `provider: kvmem`@27182——直接跑会在 16G 卡同时拉起两个 27B 实例（OOM）。已改为从 `llm.yaml` 解析 provider/base_url：kvmem→`start-llm.sh kvmem`，qwen-local→vanilla，云 provider 跳过本地启停；互斥端口被占拒绝启动（与 start-llm.sh 契约一致，任意绑定地址口径）。
- **所有权语义**（测试中误杀生产实例的教训固化）：自启动实例退出时关闭（用完必关不变；就绪后回读端口真实 pid——kvmem 的 bash 包装进程自检后先退，只杀包装会泄漏服务进程）；端口已在线实例复用但退出**不杀**（可能是用户手动启动）；互斥端口被外部占用**报错拒绝**，绝不替用户杀进程；目标端口被占但健康未过同样报错退出（可能是用户正在启动、模型加载中）。

## 6. KVMem 去留分析（加速比未达标为何仍维持）

1. **2× 通过线是 Q3 决策的"切换"门槛而非"回滚"门槛**：#57 质量门已判 KVMem 通过（有保留）并定为生产；本次的 2× 线用于评估"是否值得为一个未兑现的预期额外投入"，实测证明 2× 从物理上不可达（step4 排队主导），继续以 2× 为尺只会否定一个已稳定运行的方案。
2. **加速比 1.18× 是最差项目的数字**：step7 实测 3.0×、历史负载下 step4+step7 合计快 32-58%（§2.3）、短调用延迟 2.7×（#57 微基准）、启动自检 87-100 t/s 恒定。
3. **旧栈回滚无收益**：IQ3_XS 权重大 1.6G+、短延迟劣 2.7×、step7 劣 3×；唯一优势（长生成 tok/s 63 vs 71，#57）在 Daily 负载形态中不占主导。
4. **保留意见**（与 #57 一致）：若未来某日出现弱质稿凭 IQ2_S 评分挤进 top10，重跑 #57 双 leg 基准复核。
